# Local transcription runtimes and deployment options

Research for comentator/tdesktop #2, parent wayfinder #1. Evidence retrieved **2026-10-10**; repository baseline **`28ac576967a1026ecc89a927360fa0e138d7c88c`**. This is planning research, not a backend decision or implementation.

## Scope and evidence boundaries

The required behavior is manual, non-Premium transcription of **voice messages and video messages**, with audio and transcripts remaining on-device, multilingual automatic language handling plus a manual override, approved model downloads and local model import, and local transcript persistence. Ordinary video attachments, translation and server fallback are out of scope. German accuracy outranks speed; German quality selection is researched separately.

**No inference runs, benchmarks, model downloads, builds, tests, linters or formatters were performed.** Resource figures below are upstream documentation or upstream observations, not measurements of Telegram Desktop. Platform support advertised upstream is not proof of compatibility with this application's older operating systems, packaging or every downstream Unix target. Recommendations are marked as proposals; missing evidence is explicitly an unknown.

## Telegram Desktop coverage is broader than modern 64-bit Linux/macOS/Windows

At the pinned baseline, the [README](https://github.com/comentator/tdesktop/blob/28ac576967a1026ecc89a927360fa0e138d7c88c/README.md#L15-L36) advertises Windows 7+ **x86 and x64**, macOS **10.13+**, Linux 64-bit static builds, Snap and Flatpak. The [release artifact list](https://github.com/comentator/tdesktop/blob/28ac576967a1026ecc89a927360fa0e138d7c88c/Telegram/build/release.py#L211-L249) also includes Windows ARM; the scout identifies that target as ARM64 from the [CI matrix](https://github.com/comentator/tdesktop/blob/28ac576967a1026ecc89a927360fa0e138d7c88c/.github/workflows/win.yml#L50-L62). Windows 7 support must not be extrapolated to ARM64.

The [macOS build](https://github.com/comentator/tdesktop/blob/28ac576967a1026ecc89a927360fa0e138d7c88c/Telegram/build/build_mac.py#L149-L195) assembles x86_64/arm64 slices, requires identical bundle resources and merges Mach-O files; [configuration](https://github.com/comentator/tdesktop/blob/28ac576967a1026ecc89a927360fa0e138d7c88c/Telegram/build/build_mac.py#L238-L265) preserves the 10.13 deployment target. The repository's [platform convention](https://github.com/comentator/tdesktop/blob/28ac576967a1026ecc89a927360fa0e138d7c88c/AGENTS.md#L403-L431) explicitly says **all-other includes BSD variants and more**, not just Linux. Official download targets, CI coverage and downstream source portability are different sets. The shared CMake-helper submodule was empty in the read-only scout, so a complete downstream architecture/dependency-default matrix was not established.

**Consequences:** Windows x86, old macOS, Windows ARM64 and BSD must stay in the compatibility worklist. No candidate is proven here to satisfy every target unchanged. An unavailable accelerator can use a local CPU path; an unavailable backend cannot silently cause cloud fallback or removal of required platform coverage.

### Language semantics are not interchangeable

Original OpenAI Whisper `tiny/base/small/medium/large` multilingual models and `turbo` support multilingual transcription; `tiny.en/base.en/small.en/medium.en` are **English-only**, not smaller multilingual substitutes. OpenAI documents speech language identification, and whisper.cpp lists `large-v1/v2/v3` and `large-v3-turbo`. German therefore requires a suitable multilingual or explicitly German-compatible model. Fine-tunes/distilled derivatives must be checked individually: the original naming rule does not prove retained languages in an arbitrary derivative. [W3,A1]

- **whisper.cpp:** `language = nullptr`, empty or `"auto"` requests detection; an explicit language code requests that language. `translate = false` is required for this scope. [W2]
- **CTranslate2:** `detect_language` returns language probabilities; explicit language selection is supplied through Whisper's prompt/token sequence, not a turnkey `transcribe(language=...)` C++ call. Native embedding must implement the same task/language-token contract and audio feature processing. **faster-whisper** supplies `language=None` detection (documented first 30 seconds) or a manual code and `task="transcribe"`. [C1,F2]
- **sherpa Whisper:** empty language infers language for multilingual models; a code overrides it; `.en` models support only English. Task defaults to `transcribe`. [S3]
- **Parakeet TDT v3:** NVIDIA describes automatic multilingual transcription **without prompting**. This is not evidence of a separately exposed language-ID confidence or a forced-language decoder control. The inspected sherpa transducer configuration only has encoder/decoder/joiner paths, not a Whisper-style language parameter. A manual forced-language requirement is an unresolved gap for this model alone, not something to relabel as implemented. [N1,S2]
- **sherpa Canary 180m-flash:** source/target codes are explicit; empty means **English**, not auto-detect. Set source and target to the same requested language for transcription, never rely on English defaults for German. Separate language detection would be needed for automatic mode. [S4,S9]
- **Vosk:** selection of a language-specific model is the manual choice. Auto-routing would need separately evidenced local language identification, additional model availability and cost. [V2,V3]

## Deep runtime notes

### 1. whisper.cpp

The library accepts 16 kHz float PCM and handles log-Mel features, encoder, decoder and text results. Its API loads from a local ggml file, memory buffer or caller-supplied reader; this is not an arbitrary PyTorch checkpoint or GGUF import promise. Conversion from original OpenAI/Hugging Face checkpoints is a separate toolchain step. Model files can be imported already converted, without shipping Python to end users. Integer quantization is supported, but its German-quality effect is unmeasured here. [W2,W3]

Baseline build uses C/C++/CMake and vendored ggml; optional accelerators add their own dependencies. Disable standalone tools/server/examples and keep `WHISPER_CURL` off for an embedded inference-only build. The README's “without dependencies” claim describes the lightweight baseline, not every optional backend. CUDA/Vulkan/ROCm add toolkit/driver and redistribution considerations; OpenVINO and Core ML encoder paths add converted sidecar artifacts. [W1,W4]

Metal offers an Apple-specific local accelerator without requiring the Core ML export workflow. Core ML runs the **encoder** on the Apple Neural Engine, requires a matching `.mlmodelc` companion and has device-specific first-run compilation. Upstream recommends macOS 14+ for that path due to possible issues on older systems; it does not establish support back to Telegram's 10.13 baseline. Do not treat upstream acceleration ratios as Telegram measurements. The newly documented ANEForge route produces a bundle tied to the generating machine/OS build; it is not an obvious universal redistribution artifact. [W1]

`n_threads`, progress/new-segment callbacks, an encoder-begin callback and `abort_callback` support worker integration. The release notes include abort callback support during language detection. A context must not be used concurrently by multiple threads; `whisper_full_parallel` explicitly warns that independent chunk boundaries can worsen accuracy. Cancellation API presence does not establish cancellation latency inside each accelerator kernel, model loading or all preprocessing. These are later measurements. [W2, release v1.9.5]

### 2. CTranslate2 is native; faster-whisper is not its C++ transcription API

CTranslate2 can be compiled as a native C++17 library without its Python wrapper. Its documentation asks for CMake 3.15+; the inspected v4.8.2 top-level source declares 3.7, so use the stricter documented prerequisite for planning rather than claim the older declaration proves a working minimum. CPU builds choose math backends; Apple Accelerate is a CPU backend, **not Metal GPU support**. The device enum is CPU/CUDA; the source HIP build maps into that implementation and must not be described as available in every published wheel. [C3,C5]

A native Whisper instance exposes encoding, token generation, language detection and alignment through a replica pool and `std::future` results. Telegram would still need the correct Mel features, tokenizer/vocabulary integration, 30-second/long-audio scheduling, timestamps, context and no-speech/decoding policy that faster-whisper provides. Runtime comparison must hold those policies constant; otherwise equal checkpoints can produce different quality. CT2's current speech documentation calls the speech models experimental, independently of its mature translation engine. [C1,C2,F1]

The replica-pool configuration controls threads per replica and queued batches; docs separately describe intra-operation threads and parallel workers. Futures are **not cancellation tokens**: inspected `WhisperOptions` and methods do not expose an abort/cancellation callback. Stop submitting later windows is possible **[INFERENCE]**; prompt interruption of an in-flight encode/decode is unknown. Discarding the future/result must not be presented as stopping computation. [C1,C4]

The import unit is a complete CT2 model directory (`model.bin`, configuration and vocabularies, plus transcription tokenizer/preprocessor metadata where needed). Conversion is ordinarily Python/offline preparation, not inference. Converted models are portable across OS/architecture with the same endianness; loader versions older than the converter are not guaranteed compatible. [C6]

**Network trap:** faster-whisper's size/name constructor automatically downloads from the Hub. Local paths and `local_files_only` exist, but v1.2.1 source still calls `Tokenizer.from_pretrained` if `tokenizer.json` is absent; that fallback is not passed the constructor's offline flag in the inspected code. An approved complete package and absence of convenience Hub loading are necessary. This is a concrete code path, not a claim that CT2 native inference itself needs a network. [F1,F2]

CUDA version documentation is inconsistent: CT2 4.8.2's install page mentions CUDA 12/cuDNN 8, while faster-whisper v1.2.1 explicitly calls for CUDA 12/cuDNN 9 for recent CT2 releases. Native source has optional cuDNN linkage. Pin an actual native build/provider ABI and audit its dependencies; do not copy either broad requirement as a universal supported combination. [C3,C5,F1]

### 3. sherpa-onnx: credible equivalent route, with exact-model and dependency caveats

The native C/C++ API takes float waveforms with their sample rate, creates streams and decodes them; configurations carry model paths, token tables, provider and `num_threads`. It offers feature extraction and model-specific decoding, unlike treating ONNX Runtime alone as a complete speech recognizer. Models must match the implemented input/output/metadata/decoder contract. A `.onnx` suffix, a NeMo origin or a successful export is not sufficient. [S2,S3,S4]

Concrete non-Whisper evidence:

- **`nvidia/parakeet-tdt-0.6b-v3`**: sherpa documents its converted encoder/decoder/joiner int8 bundle and explicit `nemo_transducer` usage; the release tree includes a v3-specific exporter. It supports 25 European languages including German; v2 is English-only. NVIDIA's model card at `541d1f99c6b0c3cd0b11a95167540bb8edefd82b` declares CC-BY-4.0. This is a credible accuracy candidate, not a German winner or demonstrated forced-language solution. [S8,N1]
- **`nvidia/canary-180m-flash`**: an explicit sherpa exporter/recognizer supports English/German/French/Spanish using source/target language codes; card at `b12ab418510d093e83890178fd0e8b0d0f7918a6` declares CC-BY-4.0. **`nvidia/canary-1b-v2` is a different model**; its card at `d455706339a6b32e1aa40f82c713a482a0c938e2` lists 25 languages and CC-BY-4.0, but this research did not establish a supported native sherpa or CT2 deployment for that exact variant. The inspected sherpa release only supplies the 180m-flash exporter and four-language Canary configuration. Its quality-research candidacy must not become an unsupported runtime-compatibility claim. [S4,S9,N2,N3]
- SenseVoice's documented language set is Chinese/Cantonese/English/Japanese/Korean, and the listed Moonshine tiny model is English; neither is a German-first replacement on that evidence. Other Zipformer/CTC models are model-specific possibilities, not universal multilingual equivalence. [S1]

Build requirements include C++17, CMake 3.15+ and ONNX Runtime, kaldi-native-fbank, kaldi-decoder, simple-sentencepiece and JSON support. The default project also enables optional websocket/binaries/TTS/diarization features. An ASR-only embedding should disable those unused features and their dependencies rather than inherit unrelated server or speech-synthesis packaging. Build-time FetchContent/downloads are distinct from offline inference; dependencies should be pinned/supplied through the repository's preparation/package conventions. [S6]

Provider names are not guarantees: Core ML requires a suitable Apple ORT build/model; DirectML has a Windows x64 acquisition path; CUDA requires matching ORT/toolkit libraries. CPU fallback for unsupported nodes or providers must be characterized. The stock ORT acquisition switch explicitly ends in a fatal error for unlisted operating systems; BSD needs a documented system/source ORT route or upstream work, not a Linux prebuilt binary. [S5,S6]

Two version traps matter: sherpa sets a top-level macOS deployment target of 10.14, already newer than Telegram's 10.13; current ORT build docs say 13.3 for standard macOS artifacts and no longer support 32-bit Windows builds. Sherpa still has x86 acquisition paths. These observations refer to **different components/releases**, so neither “Windows x86 is supported everywhere” nor “sherpa cannot run x86 at all” follows. Inspect each selected ORT artifact and its actual loadable OS/ISA floor. [S6,O1]

The inspected offline recognizer API is synchronous and does not expose a cancellation handle or application-controlled `Ort::RunOptions`. ONNX Runtime itself exposes `RunOptions::SetTerminate`, but this does **not** make it accessible through the stock sherpa API. Cooperative cancellation between application-managed segments is plausible **[INFERENCE]**, while robust interruption of in-flight decoding is unresolved. Thread controls exist; concurrent recognizer mutation/decoding and memory sharing need an explicit ownership policy and validation. [S2,O2]

### 4. Vosk, raw ONNX Runtime and reference Python implementations

Vosk is a credible CPU/incremental comparison with German model availability and a simple C embedding boundary. Its models are Kaldi directories; a Vosk model may be shared across processing threads, while each recognizer usually runs in its own thread. `accept_waveform`, partial/final results, reset and free permit cancellation between submitted PCM chunks **[INFERENCE]**, but the inspected API has no asynchronous in-call abort. Source builds require Vosk's Kaldi fork, OpenFST, OpenBLAS/CLAPACK or MKL and optional CUDA; upstream warns building is not straightforward. [V1,V2]

Its installation page includes old Python-version guidance and an explicit Windows ARM64 exclusion; do not use that as a complete current native build matrix. Its model catalogue is valuable evidence of **per-model** licensing, but published model WERs are not compared here to rank German quality. [V1,V3]

**Raw ONNX Runtime** is MIT-licensed inference infrastructure, not a ready-made ASR backend: frontend features, tokenizer, architecture-specific state/decoding, language policy and long-message handling remain application responsibilities. Prefer evaluating a proven integration such as sherpa before proposing a new ASR implementation. ORT's operator/IR/provider version compatibility is another model-import boundary. [O1,O3,S2]

**OpenAI Whisper / Transformers / NeMo Python** can perform local inference and remain useful quality-reference/export tooling. Python is not inherently online-only. However, shipping such stacks adds interpreter and framework/model-library dependencies, does not supply the native Telegram integration boundary, and still needs a platform/package/licensing solution. Original Whisper additionally documents PyTorch, tokenizer dependencies and command-line FFmpeg. No Python-side result should be assumed to reproduce a native conversion unchanged. [A1,F1,S7]

### 5. Native OS APIs are not a universal backend

**Apple:** the older `SFSpeechRecognitionRequest.requiresOnDeviceRecognition` prevents audio being sent over the network only when the recognizer's `supportsOnDeviceRecognition` is also true. It must fail closed if that condition is absent, not transparently use a server. Modern `SpeechAnalyzer`/`SpeechTranscriber` is a genuine Apple-native comparison point: macOS 26+ availability, runtime device/locale checks, asynchronous input/results and `cancelAndFinishNow`. Apple describes on-device processing in its WWDC25 session. Models are downloaded from Apple and managed/updated by `AssetInventory`; applications do not work directly with model assets. This cannot cover old macOS, Windows/BSD or arbitrary local model import. No German quality conclusion follows from an OS API's existence. [P1–P3]

**Windows:** do not describe every Windows speech API as offline. Microsoft's older UWP predefined dictation/web-search grammars use a remote service and require networking; local custom grammars do not establish general free-form message transcription. Conversely, the newer Windows AI speech API documentation retrieved at commit **`a43f5b67d189ff9f117fbf039426d95976941e99`**, updated **2026-10-08**, explicitly supports on-device file/stream transcription on NPU **and CPU**, not GPU. It requires Windows 11 24H2+, experimental App SDK 2.2.2-experimental9+ and declares **not supported for production / do not publish to Microsoft Store**. CPU models may download through Windows Update after `EnsureReadyAsync`; do not repeat older generic claims that this API is NPU-only. Locale/auto-detection/manual-override semantics and exact model redistribution/import are not established by that overview. Even if it stabilizes, it is not a cross-platform answer. [P4,P5]

## Licenses and redistribution gates

The application is [GPLv3-or-later with an OpenSSL linking exception](https://github.com/comentator/tdesktop/blob/28ac576967a1026ecc89a927360fa0e138d7c88c/LEGAL#L6-L17). The exception is not a blanket exception for arbitrary accelerator libraries.

- **Code:** whisper.cpp, CTranslate2 and faster-whisper are MIT; sherpa-onnx and Vosk API are Apache-2.0; ONNX Runtime is MIT. Preserve license/copyright notices and Apache notice/modification obligations where applicable. These top-level code licenses are promising, **not blanket clearance of the complete linked dependency graph**. [L1–L5,V2]
- **Original OpenAI weights:** OpenAI explicitly releases code **and model weights under MIT**. Retain provenance and notices when converting/quantizing. A runtime's MIT license alone would not establish this. [A1]
- **NVIDIA examples:** Parakeet TDT v3, Canary 180m-flash and Canary 1b-v2 cards declare CC-BY-4.0, not the sherpa/NeMo code license. Redistribution of converted weights needs appropriate attribution, license link and indication of changes under the [CC-BY-4.0 legal code](https://creativecommons.org/licenses/by/4.0/legalcode.en). Check the exact downloaded revision and associated notices. [N1–N3]
- **Vosk/third-party weights:** catalogue licenses vary: Apache-2.0 German small-de-0.15/de-0.21/de-tuda; LGPL-3.0 for small-de-zamia; other language entries include AGPL, GPL and noncommercial CC-BY-NC-SA. An approved catalogue must be artifact-specific; a list of “Vosk-supported models” is not an unrestricted redistribution list. Fine-tuned Whisper weights likewise need their own model-card/license review. [V3]
- **Dependencies and accelerators:** BLAS/OpenMP/ORT transitive code, CUDA/cuDNN, ROCm/OpenVINO and vendor NPUs have independent redistribution terms, binary dependencies and sometimes proprietary components. Audit exact builds against GPL and each package channel; dynamic loading or moving inference to a helper process is not by itself a license-compliance solution. This research does not provide legal clearance. [C3,C5,S6,W1]
- **Native OS models:** APIs expose OS-managed availability, not a grant to redistribute/export their model assets. Their systems' model download/import lifecycle is materially different from importing an approved portable file. [P3,P4]

## Proposed packaging approach, not a product decision

**Proposal:** evaluate a pinned native CPU-capable runtime shipped with the app/package and **separately managed model-data packages**. Keep the model catalogue/downloader independent from inference. Do not require Python, a shell, `pip`, Git LFS, a vendor account or an inference network connection on an end user's machine. Python/export dependencies can live in reproducible model preparation, where license provenance and compatibility are reviewed. These proposals follow the native loaders and documented conversion paths; they do not select a backend. [W2,W3,C6,S7]

1. **Approved download and local import converge on one complete compatible data package.** Record runtime/model-format revision, exact checkpoint/converter, supported languages/tasks, precision, required files, expected size/checksum and model/code notices. Treat source checkpoints, ggml, CT2 directories and ONNX bundles as different formats. Local import means compatible model data, not arbitrary Python/pickle code execution or downloading user-supplied runtime libraries. A format-appropriate import flow remains a later design decision.
2. **Inference loads only installed local paths/buffers.** No named-model Hub constructor, missing-tokenizer download or upstream CLI downloader in the transcription path. Consent applies to model acquisition, not permission to upload content. Missing assets produce a local unavailable/error state. Do not confuse obtaining Telegram's original message locally with sending it to an ASR service. [W4,F1,F2]
3. **CPU is the portability baseline; acceleration is optional and qualified per package.** Do not silently raise macOS/Windows/Unix baselines because an accelerator or ORT binary requires a newer OS. Modern provider binaries may need conditional loading, source builds or a different candidate; the coverage solution remains unresolved. A separate signed helper may improve failure/isolation/cancellation behavior **[INFERENCE]**, but adds IPC/packaging and does not remove runtime compatibility or licensing work. In-process library versus helper remains open.
4. **Follow existing channels, not a new ad-hoc binary downloader.** macOS dylibs/helpers need matching universal slices, identical architecture-neutral resources, app-relative loading and the existing hardened signing/notarization path; a [Swift runtime bundling precedent](https://github.com/comentator/tdesktop/blob/28ac576967a1026ecc89a927360fa0e138d7c88c/Telegram/cmake/telegram_apple_swift_runtime.cmake#L27-L43) already exists. [Signing/notarization](https://github.com/comentator/tdesktop/blob/28ac576967a1026ecc89a927360fa0e138d7c88c/Telegram/build/build.sh#L413-L419) must include added executable code; model data should not be confused with executable plug-ins. Windows EXE/portable/Store architecture artifacts must package the corresponding runtime dependencies. All-other system packages should retain source/system-library routes; Snap/Flatpak need writable persistent model locations and local-import sandbox access, rather than writing into the installed app image.
5. **Sandbox and persistence are application responsibilities.** The [Mac Store entitlements](https://github.com/comentator/tdesktop/blob/28ac576967a1026ecc89a927360fa0e138d7c88c/Telegram/Telegram/Telegram%20Lite.entitlements#L5-L22) provide user-selected file access and app-scoped bookmarks; [Snap](https://github.com/comentator/tdesktop/blob/28ac576967a1026ecc89a927360fa0e138d7c88c/snap/snapcraft.yaml#L5-L28) is strictly confined. Exercise actual model import/copy/access across launches. Runtime models/caches are **not transcript persistence**: Telegram must own local transcript storage, message association, restart behavior and deletion semantics without synchronizing transcripts to a remote service. This note does not decide the storage schema or retention UX.
6. **Audit offline behavior beyond weights.** Optional network modules should be absent from inference builds; avoid transcript-bearing logs/crash payloads and audit all enabled provider paths. ONNX Runtime exposes `DisableTelemetryEvents`, with docs saying telemetry is on by default; determine exact selected build behavior and whether the sherpa environment exposes the control. This is not evidence that it uploads audio/transcripts, nor proof of zero egress. The Telegram app itself needs network access, so privacy validation must distinguish normal Telegram/model-download traffic from inference content or dependency telemetry. [O4,S6]

## Shortlist and precise follow-up questions

**Keep three primary native routes for evaluation, with no final ordering by German quality:**

1. **whisper.cpp + full multilingual Whisper** as the direct embedded, broad-portability reference route; include large-v3, turbo and a smaller multilingual checkpoint/precision variant only as evaluation configurations, not a selected default.
2. **CTranslate2 C++ Whisper**, with faster-whisper as an orchestration/reference comparison rather than assumed embedded API. Resolve native preprocessing/decoding ownership, cancellation and Windows/BSD coverage before equating it with a shippable wrapper.
3. **sherpa-onnx**, comparing its Whisper path and explicitly supported **Parakeet TDT v3 / Canary 180m-flash** paths. Their auto/manual language differences, exact licenses and ORT target floors are gates. Canary 1b-v2 remains a quality candidate with an unresolved native deployment prerequisite, not a promised compatible model.

**Secondary:** Vosk for an established incremental/low-footprint language-model comparison if German quality and language-routing requirements justify its extra work. Apple modern speech APIs and new Windows AI speech remain platform-specific reference studies, not the universal fallback. Small/fast/quantized models must not win solely on speed or installer size.

Proposed later investigations (not conducted here):
